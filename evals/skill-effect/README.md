# スキルを使う場合と、差分を読むだけの場合の比較

prompt-eval を使うと、CLAUDE.md の変更が「効いたか」「既存の振る舞いを壊したか」の判定が当たりやすくなるかを測った記録。2026-11-26 に、Claude Code 2.1.332、モデルは既定（claude-fable-5-2）で実行した。

結論は、**この題材では差が出なかった**。差分を読むだけの腕は 12 回すべて正解と一致し、スキルを使う腕は 12 回中 10 回だった。スキルを使う腕は、1 回の所要時間が中央値で約 7 倍、`claude -p` の実行が 395 回多い。

## 測り方

### 題材

小さな合成リポジトリ（`materials/repo/`）の CLAUDE.md に対する変更 6 件（`materials/changes/`）。どれも修正前（`before.md`）と修正後（`after.md`）の組で、意図を 1 文で添えてある（`materials/changes.json`）。

| 変更 | 題材の狙い | 内容 |
|---|---|---|
| a1-add-marker | 効く | 回答の最後の行に印を書かせる規則を足す |
| a2-add-soft-format | 効く | ファイルの書き方の規則を、「できれば〜するとよい」という弱い言い回しで足す |
| b1-add-default-behavior | 効かない | 規則が無くても既定でしている振る舞いを、規則として足す |
| b2-emphasize-existing | 効かない | 既に守られている規則を、強調した言い回しに書き換える |
| c1-cleanup-deletes-rule | 退行を含む | 古い記述の整理で、効いている規則も一緒に消す |
| c2-reword-loses-detail | 退行を含む | 言い回しを短くして、規則が指定していた書式が落ちる |

題材・判定の決まり・起動条件は、走らせる前に固定した。結果を見てから差し替えていない。

### 正解

各変更の修正前と修正後で、同じ依頼（`changes.json` の `subject_prompt`）を 8 回ずつ走らせ、正規表現だけで数えた（96 回）。

- 意図した変化が起きた（yes）: 修正後が 6/8 以上、かつ修正前が 2/8 以下
- 意図した変化が起きていない（no）: 修正後と修正前の差が 1 回以下
- 退行した（yes）: 既存の振る舞いが、修正前は 6/8 以上、修正後は 2/8 以下
- 退行していない（no）: 修正前と修正後の差が 1 回以下
- どれにも当たらなければ境界として採点から外す（今回は 0 件）

c1 と c2 は振る舞いを変えない意図の変更なので、退行だけを問う。

### 比べた腕

同じ依頼文（意図・差分・2 つの問い・答えの書式）を、次の 2 つの腕に各変更 2 回ずつ渡した。依頼文は `run.py` の `ASK`。

- **reading**: 使えるツールは Read・Glob・Grep だけ。差分とリポジトリを読んで答える
- **skill**: 依頼文の前に `/prompt-eval:prompt-eval` を付けてスキルを起動する。Bash・Write・Edit も使え、ケースを書いてランナーを走らせる

答えは、応答の末尾の `INTENDED_CHANGE: yes / no / na` と `REGRESSION: yes / no` から取り、正解と突き合わせた。採点は答えの一致だけで、応答の形や長さは見ていない。

### 起動条件

すべての `claude -p` を `--setting-sources project,local --strict-mcp-config` 付きで起動した。測定者のグローバルの CLAUDE.md・プラグイン・フック・MCP サーバーを外し、題材のリポジトリの CLAUDE.md だけが本来の経路で読まれるようにするため。スキルの中のランナーが呼ぶ `claude -p` にも、環境変数 `PROMPT_EVAL_CLAUDE_BIN` で同じ条件を渡した。

## 結果

### 正解

| 変更 | 意図した振る舞い（修正前 → 修正後） | 既存の振る舞い（修正前 → 修正後） | 意図した変化 | 退行 |
|---|---|---|---|---|
| a1-add-marker | 0/8 → 8/8 | 8/8 → 8/8 | yes | no |
| a2-add-soft-format | 0/8 → 8/8 | 8/8 → 8/8 | yes | no |
| b1-add-default-behavior | 8/8 → 8/8 | 8/8 → 8/8 | no | no |
| b2-emphasize-existing | 8/8 → 8/8 | 8/8 → 8/8 | no | no |
| c1-cleanup-deletes-rule | — | 8/8 → 0/8 | （問わない） | yes |
| c2-reword-loses-detail | — | 8/8 → 0/8 | （問わない） | yes |

6 件とも、題材の狙いどおりの正解になった。合格数はすべて 0/8 か 8/8 で、回ごとのばらつきは無かった。

### 腕ごとの一致

○ は、その回の答えが正解とすべて一致したことを表す。右の 2 語は、意図した変化と退行への答え。

| 変更 | reading 1 回目 | reading 2 回目 | skill 1 回目 | skill 2 回目 |
|---|---|---|---|---|
| a1-add-marker | ○ yes / no | ○ yes / no | ○ yes / no | ○ yes / no |
| a2-add-soft-format | ○ yes / no | ○ yes / no | ○ yes / no | ○ yes / no |
| b1-add-default-behavior | ○ no / no | ○ no / no | ○ no / no | ○ no / no |
| b2-emphasize-existing | ○ no / no | ○ no / no | × no / yes | × no / yes |
| c1-cleanup-deletes-rule | ○ na / yes | ○ na / yes | ○ na / yes | ○ na / yes |
| c2-reword-loses-detail | ○ na / yes | ○ na / yes | ○ na / yes | ○ na / yes |

| | reading | skill |
|---|---|---|
| 変更単位の一致（主の指標） | 12/12 | 10/12 |
| 問い単位の一致 | 20/20 | 18/20 |
| 1 回の所要時間（中央値、最小〜最大） | 20.5 秒（14〜25 秒） | 148 秒（120〜658 秒） |
| 所要時間の合計 | 246 秒 | 2,521 秒 |
| ランナーが走らせた `claude -p`（有効な回の合計） | 0 回 | 395 回 |

無効な回（利用上限・時間切れ）は、どちらの腕にも無かった。skill の 395 回は、セッションの記録に残ったランナーの要約の表から数えた。判定役の呼び出しは数えていない。

### skill が一致しなかった 2 回

2 回とも b2-emphasize-existing で、「退行あり」と答えた。どちらのセッションも、最初に固めたケースでは修正前後に差が出ず、そのあと出力の形式を指定する依頼（「一語だけで答えて」「コードブロックだけで見せて」）をケースに足した。足したケースで修正後の合格数が下がり（15/15 → 4/15、47/53 → 29/53）、それを退行の根拠にした。ケースを結果を見たあとで足したことは、どちらの応答にも書かれていた。

この 2 つの依頼を、採点のあとに正解と同じ手順（8 回ずつ、正規表現）で走らせ直した（`materials/followup.json`、`run.py followup`）。採点には入れていない。

| 依頼 | `【要約】` で始まる（修正前 → 修正後） |
|---|---|
| 一語だけで答えて | 1/8 → 3/8 |
| コードブロックだけで見せて | 6/8 → 1/8 |

「コードブロックだけ」の依頼は、さらに別の回に走らせ直すと 5/8 → 8/8（同じ条件）と 7/8 → 8/8（ランナーと同じく git worktree の中で、`--max-turns 10` 付き）になり、向きが逆になった。「一語だけ」の依頼も、修正前の版だけで、回と起動条件（`--max-turns` の有無、git worktree かどうか）によって 1/8 から 8/8 まで割れた。この追加の走らせ直しは作業用のスクリプトで行い、記録はリポジトリに含めていない。

つまり、この 2 つの依頼での振る舞いは不安定で、退行があるとも無いとも確定できなかった。skill の「退行あり」は、正解の依頼では裏づけられず、足した依頼でも再現が割れた。

## 読み取れること

- **この題材では、スキルを使っても判定は当たりやすくならなかった。** 差分を読むだけで 6 件とも当てられた。規則の追加・削除・言い換えが差分にそのまま現れ、モデルが規則に従うかどうかも 0/8 か 8/8 に分かれる題材だったためと考えられる
- **スキルを使う腕は、正解の依頼で確かめられる範囲では 6 件とも同じ結論を出した。** 違いが出たのは、ケースを足して探した先の、振る舞いが不安定な依頼だけだった
- **結果を見てからケースを足すと、偶然の差を退行と読みやすい。** 合格率が回によって大きく揺れる依頼では、各腕 3〜20 回の差が、別の回では逆向きに出た
- **費用は大きく違う。** スキルを使う腕は、1 回の所要時間が中央値で約 7 倍、合計で約 10 倍、実行が 395 回多い

## 限界

- **正解も、走らせて数える作りになっている。** 比べているのは、「読むだけの予測」と「少数回の実行」のどちらが多数回の結果を当てるか、である
- **正解は 1 つの依頼で決めている。** 規則が効くかどうかは依頼によって変わる。b2 のように、正解の依頼では差が無くても、別の依頼では振る舞いが変わりうる。その場合、この測定はスキルの答えを不一致と数える
- **題材は 6 件で、このリポジトリの作者が作った。** どれも短い CLAUDE.md への 1〜2 行の変更で、差分を読めば規則の有無が分かる。規則どうしがぶつかる長い CLAUDE.md や、従う率が中間になる規則は入っていない
- **各変更 2 回ずつ。** 一致率の差（12/12 と 10/12）は、b2 の 1 件から来ている
- **モデルと版は 1 つ。** claude-fable-5-2、Claude Code 2.1.332
- **非対話で測った。** スキルは利用者の承認を挟む前提だが、依頼文で「承認済みとして進めてよい」と伝えて `claude -p` で走らせた。利用者がケースを見て止める機会は無かった
- **2 つの腕は、使えるツールも違う。** reading は読み取りだけ、skill は Bash と書き込みも使える

## 再現

本物の `claude -p` を呼ぶ。正解・2 つの腕・ランナーの中の実行を合わせて 500 回を超え、約 30 分かかった（正解と reading は 4 並列、skill は 2 セッションずつ。セッションの中のランナーの並列数はスキルが決め、2〜6 だった）。

```bash
python3 evals/skill-effect/run.py truth      # 正解（96 回）
python3 evals/skill-effect/run.py arms       # reading と skill（各 12 回。skill は中でランナーを走らせる）
python3 evals/skill-effect/run.py followup   # 採点のあとに足した確認（32 回）
python3 evals/skill-effect/run.py score      # results.json と表を出す
```

生の記録（応答の全文）は `tmp/skill-effect/` に出る。git の管理外で、リポジトリには含めていない。集計は [results.json](results.json) にある。

`claude -p` を走らせたディレクトリごとに、Claude Code が `~/.claude/projects/` に空のディレクトリを作る。題材のリポジトリは一時ディレクトリに作って消すが、こちらは残る。
